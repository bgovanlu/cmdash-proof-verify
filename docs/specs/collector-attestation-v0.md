## 1. What it proves, and why it is a companion

A proof receipt says "the issuer signed that n of d items met the control". For a measurement taken by a customer-run
collector (source kind `COLLECTOR`, receipt spec §5.6), the issuer is the tenant's key, which on SaaS CMDash holds
(receipt spec §6.4). A relying party could fairly ask: did the number come from inside the supplier's network, or did
the platform make it up?

A **collector attestation** answers that. The supplier's collector holds its own Ed25519 key, generated inside the
supplier's boundary; CMDash only ever sees the public half. The collector signs each measurement it takes. A receipt
built from that measurement names the collector key in its signed `sources`, and the collector's signature over the
same counts, time and issuer travels next to the receipt as this document.

**Why a companion, not a receipt member.** Receipt v0 is closed (receipt spec §13): a new payload or envelope member
would be a v1, and every deployed v0 verifier would answer UNVERIFIABLE for every collector-attested receipt. As a
companion, a collector-attested receipt is an ordinary v0 receipt (a v0 verifier says VALID, basis MEASURED), and a
verifier that knows this document additionally reports ATTESTED. The binding runs both ways through fields both
signatures already cover (§5): the issuer names the collector key and signs the method `collector-attested.<metric>.v<N>`;
the collector names the issuer, the metric, the counts and the time.

**Customer-held issuer keys** (a `CUSTOMER`-custody issuer key, receipt spec §13) are a separate, later item: this
document does not change who signs the receipt. On a **fully self-hosted deployment** the tenant's issuer key is the
customer's by construction, so there the receipt itself is already customer-signed (§8).

## 2. The collector key and its messages

- **Key.** Ed25519. Generated by the collector (`cmdash-collector enroll`), written to a file the collector creates with
  mode 0600 and refuses to overwrite; a file other users can read is refused at load. The private key is never sent,
  logged or printed.
- **Key id.** `cmdash-collector-` + the first 16 lowercase hex of SHA-256 over the DER SPKI: the receipt spec §6.1 rule
  with its own prefix, so a collector key id can never be read as an issuer key id.
- **Messages.** The key signs exactly four kinds of message, each `UTF-8(tag) || canonical(fields)`, where
  `canonical` is the receipt spec §3 form (strings and safe integers, members sorted by UTF-16 code unit, no
  whitespace). The form is length-unambiguous: every string is quoted and escaped and every member named, so no two
  field sets share bytes. Each tag ends in a line feed and names its purpose, so no signature crosses purposes
  (vector `C10`).

| Tag | Fields | Signed when |
| --- | --- | --- |
| `cmdash-collector-enroll-v0\n` | `enrollmentId`, `publicKey` (base64url SPKI), `tokenSha256` | registering the key (proof of possession, §4) |
| `cmdash-collector-rotate-v0\n` | `deployment`, `tenantRef`, `enrollmentId`, `oldCollectorKeyId`, `newPublicKey`, `t` | rotating, by BOTH keys (§4) |
| `cmdash-collector-push-v2\n` | `deployment`, `tenantRef`, `collectorKeyId`, `seq`, `nonce`, `t`, `bodySha256` | every push (the `v2=` of the header, §4) |
| `cmdash-collector-measurement-v0\n` | the **measurement statement** below | every attested measurement |

**The measurement statement** is a JSON object with exactly these members:

| Member | Content |
| --- | --- |
| `v` | `0` |
| `deployment` | the issuing deployment's canonical origin (receipt spec §6.2): what the receipt signs as `issuer.deployment` |
| `tenantRef` | the tenant's public issuer id (receipt spec §6.2). The internal tenant id never appears in a receipt or a statement; the tenantRef is how the tenant is inside the signed message |
| `collectorKeyId` | the signing key's id |
| `metric` | a slug naming what was counted (`edr-coverage`, `mfa-enrolled`) |
| `numerator`, `denominator`, `unknown` | integers 0 to 10⁹ with n + u ≤ d. One item per value the collector read: JSON `true` meets, `false` fails, anything else is unknown (unknown is never pass) |
| `measuredAt` | receipt spec §4 timestamp: when the collector read the target |
| `seq` | the sequence number of the push that carried it (≥ 1) |
| `nonce` | 16 random bytes, 32 lowercase hex |

## 3. The companion document

```json
{ "format": "cmdash-collector-attestation", "v": 0,
  "collectorKey": { "kid": "cmdash-collector-…", "alg": "Ed25519", "publicKey": "<base64url DER SPKI>" },
  "statement": "<base64url of the canonical statement bytes>",
  "sig": "<base64url of the 64-byte signature over the measurement tag and those bytes>",
  "revokedAt": "<optional timestamp>" }
```

- No other member; strict JSON (receipt spec §3.4), 64 KiB at most. The statement is carried as the exact signed
  **bytes**, never as an object a parser could re-read differently (receipt spec §1.1).
- `revokedAt`, when present, is the serving deployment's report that the key was revoked, unsigned. It can only lower
  a result, so it is safe to honour and removing it gains nothing a pinned revocation (§5) does not take back.
- CMDash serves it at `GET /proof/receipts/:receiptId/collector-attestation` (404 when the receipt is not
  collector-attested).

## 4. Enrollment, pushes and revocation (the CMDash side)

**Registration (key substitution).** An OWNER/ADMIN issues a one-time registration token for one enrollment
(`POST /collectors/:id/key-token`, or `POST /collectors` with `attested: true`; audited). CMDash stores only its
SHA-256; it lives 24 hours; issuing it moves the enrollment to signature version 2 for good, and from then on the
enrollment accepts **no push at all** until a key is registered. The collector registers with the token, its public key
and the enroll-tag proof of possession, through the API key the enrollment was made against. The token is consumed in
the same statement that stores the key. The key must pass the receipt spec §2.1.1 step-1 point checks and have prime
order. Key ids and SPKIs are unique across the deployment, rotated-out keys included, so one key can never serve two
enrollments or two tenants. Replacing a key takes either the rotate-tag message signed by the registered key AND the
new one (5-minute window; a replay fails because the old key is no longer registered) or a new admin-issued token.
Both are audited; the old key becomes RETIRED.

**Pushes (downgrade and replay).** HMAC (`v1=`) stays on every push for transport authentication. For an enrollment
at signature version 2 the server also requires `v2=` over the push-tag message, whose `bodySha256` covers the body,
attestations included:

- a header without `v2=` is refused (the downgrade), and so is every push while no key is registered;
- `seq` MUST be above the last one accepted for the enrollment; the floor moves in one conditional UPDATE, so two
  copies of a push cannot both pass (the replay), and `t` is within 5 minutes;
- an attested measurement is accepted only inside such a push, and only if its statement names this deployment, this
  tenant's tenantRef, the enrollment's key and the push's `seq`, was measured at most 24 hours before the push and not
  after it, carries per-item states that tally to its counts, and has a nonce the key never used (server-side
  dedupe). A v1 push that carries one is refused; nothing is ever stored as attested without a verified v2 signature.

**Receipts.** A claim generator per metric signs the newest stored measurement with `observedAt` = `measuredAt`
exactly, `freshUntil` counted from it, the counts exactly, and the one source `{ COLLECTOR, <collector key id> }`.
A receipt can therefore never claim a fresher measurement than the collector signed.

**Revocation (decided).** Revoking a collector REVOKES its keys as of that instant (`revokedAt`, recorded and
audited). Measurements it signed stay stored and receipts already built from them stay verifiable: their attestation
document carries `revokedAt`, and a verifier reports ATTESTED with that time for a receipt issued **before** it, and
MISMATCH (`collector.key-revoked`) for one issued at or after it. The cut-off is the receipt's `issuedAt`, which the
issuer signs, not `measuredAt`, which the collector signs: after a key compromise the attacker controls
`measuredAt`, never `issuedAt`. CMDash signs no new receipt from a revoked key's measurements.

## 5. Verification

`verifyCollectorAttestation(receipt, attestation, trust?)` with `trust = { collectorKeys?: [{ deployment, tenantRef,
publicKey, revokedAt? }] }`: collector keys the relying party obtained **from the supplier**, each bound to one
issuer. It performs no network access and reads no clock. The result is `{ status, rule, detail, keySource,
collectorKeyId, metric, measuredAt, revokedAt, proves, doesNotProve }`, with status ATTESTED, MISMATCH or
UNVERIFIABLE. It is separate from the receipt's verdict: ATTESTED means something only next to a VALID or STALE_VALID
receipt, and a verifier MUST verify the receipt as well (the CLI always does).

The rules, tried in this order; the first that fails is the result:

<!-- collector-rules:begin -->
| Rule | Fails when |
| --- | --- |
| `collector.receipt-undecodable` | the receipt fails the receipt spec's six structural checks (MISMATCH) |
| `collector.malformed` | the document is not strict JSON or breaks §3 (MISMATCH) |
| `collector.key-id` | `collectorKey.kid` is not derived from `collectorKey.publicKey` (MISMATCH) |
| `collector.statement-malformed` | the statement bytes are not UTF-8, not JSON, not canonical, or break §2 (MISMATCH) |
| `collector.statement-key` | the statement names another collector key (MISMATCH) |
| `collector.signature` | a receipt spec §2.1.1 rule over the measurement tag and the statement bytes (MISMATCH; `ed25519.unavailable` is UNVERIFIABLE) |
| `collector.not-measured` | the receipt is self-attested (MISMATCH) |
| `collector.issuer` | the statement's deployment or tenantRef is not the receipt's issuer (MISMATCH) |
| `collector.not-named` | the receipt's signed sources do not include `{ COLLECTOR, <this key id> }` (MISMATCH) |
| `collector.metric` | the receipt's signed `measurement.method.id` is not `collector-attested.<the statement's metric>.v<N>` (MISMATCH) |
| `collector.counts` | the statement's n, d or u differ from the receipt's measurement (MISMATCH) |
| `collector.measured-at` | the statement's `measuredAt` is not the receipt's `observedAt` (MISMATCH) |
| `collector.key-revoked` | the earliest `revokedAt` (the document's or a pinned key's) is at or before the receipt's `issuedAt` (MISMATCH) |
| `collector.key-unpinned` | collector keys were supplied and none bound to this issuer is this key (UNVERIFIABLE) |
<!-- collector-rules:end -->

`keySource` is `PINNED` when the relying party supplied the key, `ISSUER_NAMED` when only the receipt's signed
sources name it. Only a PINNED result is independent of the issuing deployment: with ISSUER_NAMED, a deployment that
fabricated both the receipt and a "collector" key of its own would be consistent. That is stated, never hidden
(`collector-key-independent` below).

## 6. What an ATTESTED result proves and does not prove

<!-- collector-proves:begin -->
| Id | Reported when | Meaning |
| --- | --- | --- |
| `collector-signed` | always | The holder of the collector key signed exactly this statement |
| `collector-bound-to-receipt` | always | That statement names this receipt's issuer, metric (through the signed method id), counts and observation time, and the issuer's signed receipt names that key |
| `collector-key-pinned` | PINNED | The key is one the relying party obtained from the supplier and bound to this issuer |
<!-- collector-proves:end -->

<!-- collector-does-not-prove:begin -->
| Id | Reported when | Meaning |
| --- | --- | --- |
| `collector-key-independent` | ISSUER_NAMED | That the key is the supplier's rather than one the issuing deployment chose: pin it (`--collector-key`) |
| `collector-source-truth` | always | That the supplier's own system reported the truth to its collector |
| `collector-key-not-revoked` | no revocation time known | That the key had not been revoked: offline verification knows only what it is given |
<!-- collector-does-not-prove:end -->

The CLI: `cmdash-verify <receipt.json> … --collector-attestation <file> [--collector-key
<deployment>#<tenantRef>=<pem>]… [--require-collector-attestation]`. Without the last flag the attestation is printed
and never changes the exit code; with it, a VALID or STALE_VALID receipt whose attestation is not ATTESTED exits 1
(MISMATCH) or 2 (UNVERIFIABLE).

## 8. Fully self-hosted deployments

On a self-hosted (on-prem or air-gapped) deployment the customer runs CMDash: the database, `CREDENTIAL_ENCRYPTION_KEY`
and therefore the tenant's MANAGED issuer key (receipt spec §6.4) are the customer's by construction; nobody else can
sign as the tenant. The receipt itself is then a customer-signed statement, and a relying party pins the tenant's key
from the customer's own key document (`--deployment <the customer's origin> --fetch`) or a key the customer hands over
(`--key`). Collector attestation adds the same thing it adds on SaaS: which collector, inside which boundary, measured
the number. Nothing in this document requires CMDash (the company) to be reachable, and nothing is sent to it.

## 9. Security considerations

| Threat | Defence |
| --- | --- |
| **v1 downgrade** (a push with only the HMAC, e.g. from someone who stole the HMAC secret out of CMDash's database) | The enrollment's own `signatureVersion` decides, never the header; at 2 a push without a valid `v2=` is refused, and an enrollment with a pending registration refuses every push. Attested measurements are accepted only under a verified `v2=`; a v1 push carrying one is refused (`COLLECTOR_ATTESTATION_REQUIRES_V2`) |
| **Key substitution at enrollment** | One-time, hashed, 24-hour token issued by an OWNER/ADMIN and audited; proof of possession over the enrollment id, the public key and the token's hash; the enrollment's own API key only; token consumed atomically with the key write; deployment-wide unique key ids and SPKIs; re-keying needs the old key's signature or a new admin token |
| **Replay of an old measurement** | Push `seq` strictly increasing per enrollment (one conditional UPDATE), `t` within 5 minutes, the statement bound to the push's `seq`, unique (key, nonce) and (key, metric, measuredAt), measurements older than 24 hours at push time refused; the receipt's `observedAt` is the signed `measuredAt`, checked by the verifier (`C06`) |
| **Cross-tenant confusion** | The tenant (as its public tenantRef) and the deployment are inside every signed collector message; the server compares them with the tenant the API key authenticated, the verifier with the receipt's issuer (`C07`) |
| **Canonicalisation ambiguity** | Signed bytes, not objects; the bytes must be the one canonical spelling (`C12`); every message is domain-tagged (`C10`) |
| **Timing** | Token hashes, key ids, API key ids and tenant bindings are compared in constant time (`timingSafeEqual` after a length check) |
| **Weak keys** | Registration runs the receipt spec §2.1.1 step-1 checks plus prime order; the verifier runs them again (`C18`) |
| **A full CMDash database compromise** | It can forge an HMAC push and flip a column, but it cannot produce a collector signature: a receipt the relying party checks against a PINNED collector key is not forgeable by the platform |
| **Revocation** | §4: keys REVOKED with the collector; receipts issued before stay verifiable and flagged; after, MISMATCH |

## 10. Known limits

- The attestation is a companion: a relying party that is never shown it sees an ordinary MEASURED receipt. A
  relying party that requires collector attestation says so (`--require-collector-attestation`) and asks for the
  document.
- ISSUER_NAMED is not independent of the deployment (§5). Only pinning makes it so.
- The per-item states are covered by the push signature, not by the portable statement: an auditor sampling an
  evidence item (receipt spec §8.3) sees what the push carried, attested to CMDash, not to the relying party.
